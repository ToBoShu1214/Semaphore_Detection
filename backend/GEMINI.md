# 🚩 旗語辨識教學系統 (Semaphore Recognition & Teaching System) - 開發紀錄文件

本文件為本專案的開發紀錄，詳盡紀錄了系統架構、通訊協議、核心演算法邏輯、軟體產品化技術以及自 2025 年 9 月啟動至今的完整開發紀錄。

---

## 一、 專案核心設計與教育願景
本專案的核心競爭力在於 **「可解釋的量化教學 (Explainable Quantitative Teaching)」**。
- **技術轉型**：捨棄傳統「影像分類 (Image Classification)」黑箱模型，改採「姿態估計 (Pose Estimation)」獲取人體骨架座標。
- **設計哲學**：將複雜的骨架座標轉換為具備幾何意義的「純向量夾角」，使系統能像人類教練一樣理解動作的結構。
- **核心價值**：透過角度偏差運算，生成具備物理空間感的校正指令（如：抬、降、跨越中線），實現真正的教學輔助而非單純的對錯判定。

## 二、 系統架構與通訊資料流 (Architecture & Data Flow)

### 1. 通訊架構 (FastAPI + React)
系統採用前後端分離架構，透過全雙工 WebSocket 連線實現低延遲同步：
- **後端 (Backend)**: Python FastAPI 負責處理影像流、YOLO 推論、FSM 狀態機轉換與校正建議計算。
- **前端 (Frontend)**: React (TypeScript) 負責 Canvas 高頻渲染、音效系統觸發與交互邏輯。

### 2. WebSocket 資料結構 (Payload Specifications)
後端傳送給前端的每一幀 JSON 數據包含以下關鍵欄位：
- `image`: Base64 編碼的 JPEG 影像。
- `state`: 目前狀態機位置（如 IDLE, READY, COOLDOWN）。
- `prompt_code`: 前端提示代碼，用於顯示顯示互動文字。
- `left_angle` / `right_angle`: 經過平滑化處理後的實時手臂角度。
- `correction_data`: 包含目標角度、誤差值與具體抬降建議（如「抬 15°」、「往對面擺」）。
- `challenge_info`: 練習進度、高亮索引與錯誤鎖定狀態。

### 3. 雙模型協同處理邏輯
- **姿態模型 (`yolo11s-pose.pt`)**：實時追蹤人體 17 個關鍵點，作為角度運算的原始資料源。
- **旗幟模型 (`flag.pt`)**：用於旗手定位。透過計算手腕點與旗幟邊界框的幾何距離進行鎖定。為優化效能，鎖定目標後會自動調降偵測頻率。

## 三、 引擎核心演算法 (Engine Core Logic)

### 1. 座標歸一化與角度計算
- **歸一化處理**：以肩膀到骨盆的中心向量作為垂直基準線，排除使用者站姿歪斜導致的誤差。
- **360° 空間向量**：使用 `atan2(y, x)` 計算雙臂向量夾角。
- **手臂伸直雙重判定 (OR Logic)**：系統結合了幾何角度與空間比例，只要滿足以下任一條件即視為伸直：
    - **角度門檻**：手肘夾角大於等於 160° (由 `STRAIGHT_ARM_THRESHOLD` 定義)。
    - **幾何比例**：手肘夾角需大於 90° (安全鎖)，且「肩膀到手腕距離」與「手臂總長」之比值大於等於 0.8 (由 `STRAIGHT_ARM_RATIO_THRESHOLD` 定義)。此機制兼顧了動作精準度與鏡頭透視造成的視覺誤差。
- **平滑化視窗**：使用 5 幀移動平均視窗消除關鍵點偵測產生的雜訊抖動。

### 2. 教學校正導引演算法 (核心亮點)
系統實作了一套基於 **180° 物理中線判定** 的抬降導引邏輯，解決了傳統角度相減在跨越身體中線時會產生指令反向的問題：
- **側別邏輯判定**：系統自動區分「對向側」與「同向側」。
- **抬降方向映射**：在同側區域時，若目前位置比目標更靠近頂點 (180°) 則提示「降」，反之提示「抬」。此邏輯在跨越 180° 分界點時會自動翻轉，確保引導始終符合物理高度直覺。

### 3. 國際旗語英數切換狀態機 (Navy System Mode Switching)
針對國際旗語中字元與數字動作重疊（如 A=1, B=2）的特性，系統實作了高度智慧化的切換邏輯：
- **模式管理 (`navy_sub_mode`)**：系統透過 `session_state` 持久化當前的子模式（ALPHA 或 NUMERIC）。
- **切換信號攔截 (`is_switch_signal`)**：
    - **數字號 (#)**：觸發後強制進入 NUMERIC 模式。
    - **字母號 (J)**：在數字模式下觸發後回歸 ALPHA 模式。
    - 這些信號在 FSM 的 `GRACE_PERIOD` 判定成功後，會被標記為切換信號，系統將執行模式更新但不將其加入單字序列 (`word_history`)。
- **智慧自動導引 (Auto-Switch Guidance)**：
    - 系統會預讀挑戰字串的下一個字元。若目標為數字但當前處於字母模式，導引序列 (`current_char_target_sequence`) 會自動被動態替換為 `['#']`。
    - 切換動作完成後，系統會立即重新計算導引目標，無縫銜接至該數字的實際姿勢。

## 四、 軟體產品化技術 (Packaging & Optimization)

### 1. 原生視窗化實作
- **啟動層 (`launcher.py`)**：整合 `pywebview` 引擎，隱藏瀏覽器組件，實現獨立軟體化體驗。
- **打包技術 (`app.spec`)**：利用 PyInstaller 進行完整封裝，解決 Uvicorn 動態加載與 Windows 路徑空格之安裝相容性。

### 2. URI 資源解析相容性修正
在打包為原生 APP 後，Webview 環境會將 URL 中的 `#` 符號解讀為「網頁錨點 (Fragment Identifier)」。
- **問題**：請求 `/digits/#.png` 會被解析為請求 `/digits/` 目錄並導航至錨點 `.png`，導致提示圖無法顯示。
- **對策**：前端在請求靜態資源時，強制使用 `encodeURIComponent()` 進行轉譯。請求路徑變更為 `/digits/%23.png`，確保後端能正確映射至磁碟上的 `#.png` 實體檔案。

### 3. GPU 硬體加速與佈署
- **硬體自適應**：自動偵測並切換 CPU/GPU 模式。
- **FP16 運算**：在 NVIDIA GPU 環境下開啟半精度運算，顯著提升偵測幀率。
- **分卷發佈策略**：採用 1500M 分卷壓縮方案，解決 GitHub Release 2GB 上傳上限問題。

## 五、 環境設置 (Environment configuration)

### A. 後端配置 (Backend)
```bash
# 建立並啟用環境
conda create -n semaphore python=3.11 -y
conda activate semaphore

# 安裝 PyTorch (以 CUDA 12.4 為例)
python -m pip install torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu124

# 安裝必要依賴項
python -m pip install fastapi uvicorn websockets numpy opencv-python ultralytics Pillow python-multipart lapx pywebview pyinstaller

# 啟動服務
cd backend
python main.py
```

### B. 前端啟動 (Frontend)
```bash
cd frontend
npm install
npm run build
```
